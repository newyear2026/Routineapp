# APP_UPDATE.md

업데이트 안내와 릴리스 노트. 판정 코드는 `lib/application/update/` 와
`lib/application/release/` 에 있고, 이 문서는 그 코드가 **왜** 그렇게 정해졌는지와
사람이 손으로 해야 하는 몫을 남긴다.

핵심 원칙 셋:

1. **강제 업데이트는 없다.** 구버전이 틀렸다고 말해 줄 서버가 애초에 없다.
2. **업데이트 안내와 릴리스 노트는 다른 기능이다.** 하나는 설치 **전**에
   무언가를 요청하고, 다른 하나는 설치 **후**에 아무것도 요청하지 않는다.
   둘이 같은 빌드를 두고 말하는 일은 없다.
3. **끼어들기는 한 번에 하나.** 다이얼로그를 쌓으면 먼저 뜬 쪽이 묻힌다.

---

## 두 기능

| | 업데이트 안내 | 릴리스 노트 |
|---|---|---|
| 언제 | 설치 **전** | 설치 **후** |
| 무엇을 | «새 버전이 있어요» | «무엇이 바뀌었어요» |
| 스토어에 묻나 | 예 (`in_app_update`) | 아니오 |
| 플랫폼 | **Android만** | 전 플랫폼 |
| 정책 | `AppUpdates` | `ReleaseAnnouncements` |
| 기기 장부 | `device.update.*` | `device.notes.*` |

---

## 안내 정책 (`AppUpdates`)

- 첫 홈 진입과 앱이 포그라운드로 복귀할 때 확인한다. 정상 확인 후 **1시간**,
  실패 후 **5분** 이내에는 자동 확인을 생략한다. 시간 경과만으로 실행하는 타이머는 없다.
- 확인 성공과 실패를 구분한다. 실패는 성공 시각이나 이미 발견한 업데이트를 지우지 않는다.
  설정에서는 확인 전·확인 중·최신·업데이트 있음·실패를 구분해 표시한다.
- 확인 시각과 실패 시각은 기기에 저장하므로 앱 재시작으로 제한이 초기화되지 않는다.
  구버전의 날짜 기록은 성공 여부를 알 수 없어 새 확인을 막는 데 사용하지 않는다.
- 동시 확인 요청은 하나로 합친다. Play 응답을 15초 동안 받지 못하면 실패로 처리한다.
- 자동 다이얼로그는 **업데이트당 한 번**. 실제로 안내를 시작한 `versionCode`와
  «나중에하기»를 저장한다. 새 버전을 발견했어도 아직 안내하지 않았다면 다음 실행에서
  표시할 수 있다. 다른 안내창이나 화면 뒤에서는 기다렸다가 홈에서 표시한다.
- 미룬 업데이트는 **배너**로 남는다. 배너를 닫으면 이번 실행까지이고 다음 실행에
  돌아온다 — 이 기능이 허락받은 최대치다.
- 설정의 «업데이트 확인»은 간격 제한을 무시한다. 성공했을 때만 앞서 누른
  «나중에»를 지워 다시 안내할 수 있게 한다. 실패는 기존 안내 상태를 바꾸지 않는다.

### 설치는 스토어 페이지로 넘긴다

In-App Update API에서 가져오는 것은 **질문뿐**이다. `performImmediateUpdate`는
구글의 전체 화면 흐름을 세우는데 그건 이 앱이 쓸 수 있는 화면이 아니고,
`startFlexibleUpdate`는 시작하지도 않은 설치를 끝낼 책임을 앱에 지운다.

### 색을 나눈 이유

배너·다이얼로그는 `orbitPrimary`(보라, 행동), 릴리스 노트는 `orbitAccent`(주황, 알림).
같은 색이면 «요청»과 «알림»이 한 기능처럼 읽힌다. 배너에 `orbitSecondary`(코랄)나
경고 톤을 쓰면 무언가 잘못된 것처럼 보이므로 쓰지 않는다.

## iOS는 왜 빠졌나

`in_app_update`는 Play Core 래퍼라 Android 전용이다. iOS까지 덮으려면 iTunes Lookup
API로 버전 이름을 견주는 포트를 따로 만들어야 하고, 그러면 **앱에 첫 외부 통신이
생겨** `PRIVACY_POLICY.md` 와 Play/App Store 데이터 안전성 신고가 함께 움직인다.

지금은 iOS가 `UnavailableUpdatePort`를 받는다. 설정의 «업데이트 확인» 행도 그 빌드에서는
**아예 그려지지 않는다** — 무엇을 눌러도 «최신 버전이에요»라고 답하는 죽은 컨트롤이
되기 때문이다. 대신 릴리스 노트는 iOS에서도 그대로 동작하므로, iOS 사용자도 업데이트
뒤에 무엇이 바뀌었는지는 받는다.

나중에 붙일 때 손댈 곳은 `AppUpdatePort` 구현 하나와 `PendingUpdate`의 식별자다.
지금은 `int versionCode`인데 iTunes Lookup은 버전 **이름**만 주므로 일반화가 필요하다.

## 릴리스를 하나 추가할 때

1. `pubspec.yaml`의 `version:` 을 올린다. `+` 뒤 versionCode도 반드시 올린다.
2. `lib/data/seed/release_notes.dart` 맨 위에 항목을 넣는다. **사용자가 알아챌 변화만**
   적는다. 변경점 전체가 내부 사정인 릴리스는 항목 없이 나가고 아무것도 알리지 않는다.
3. 줄마다 ARB 키를 세 파일(`app_en.arb`·`app_ko.arb`·`app_es.arb`)에 넣고
   `flutter gen-l10n`.
4. **항목이 5개를 넘으면 가장 오래된 것을 빼고 그 ARB 키도 세 파일에서 지운다.**
   `release_notes_test.dart`가 이 선을 넘으면 빌드를 깨뜨린다.

`1.0.0`은 목록에 없다. Figma Make 스캐폴드가 달고 있던 번호이고 스토어에 올라간
적이 없다 — 닿지 않은 버전의 «바뀐 점»은 지어낸 이력이다.

## 실기기 검증 — 자동 테스트로는 닿지 않는다

`InAppUpdate.checkForUpdate`는 **Play가 설치한 빌드에서만** 답한다. 디버그 실행,
사이드로드, Play 서비스 없는 에뮬레이터, 테스트 전부에서 예외를 던진다. 그래서
`PlayUpdatePort`는 오류를 확인 실패로 반환하며 자동 오류 팝업은 띄우지 않는다.

실제로 확인하려면 **버전이 다른 두 빌드를 같은 트랙에 올려야** 한다:

1. versionCode `N` 빌드를 내부 테스트 트랙에 올리고, 테스터 계정으로 **Play에서**
   설치한다(APK 직접 설치는 안 된다).
2. versionCode `N+1` 빌드를 같은 트랙에 올리고 배포가 끝나기를 기다린다.
3. 기기에서 Play 스토어 앱을 열어 목록을 한 번 갱신한다. Play가 업데이트를 알기
   전까지는 앱도 알 수 없다.
4. `N` 이 깔린 앱을 찬 실행으로 연다.

확인할 것:

- [ ] 홈에서 다이얼로그가 **한 번** 뜬다.
- [ ] «나중에하기» 뒤에 배너가 홈 맨 위에 남는다.
- [ ] 배너를 닫고 앱을 껐다 켜면 배너가 **돌아온다**.
- [ ] 이미 보여 준 버전의 다이얼로그는 다음 날에도 **다시 뜨지 않는다**.
- [ ] 정상 확인 뒤 1시간 이상 지나 앱으로 복귀하면 다시 확인한다.
- [ ] 확인 실패 후 5분 이내에는 자동 재시도를 생략하고, 5분 이후 다음 복귀에서 재시도한다.
- [ ] 앱을 켜두거나 백그라운드에 둔 채 시간이 지나도 주기 조회는 하지 않는다.
- [ ] 실패해도 기존 배너는 유지되고 설정에는 실패 문구가 표시된다.
- [ ] 릴리스 노트 안내를 닫거나 다른 화면에서 홈으로 돌아오면 대기 중인 안내가 표시된다.
- [ ] «업데이트하기»가 Play 목록을 연다.
- [ ] 설치를 마치고 앱을 열면 배너가 **사라진다**(자기 버전을 광고하지 않는다).
- [ ] 설정 › 업데이트 확인이 상태를 바꿔 보여 준다.
- [ ] 릴리스 노트 카드가 설치 **뒤에** 한 번 뜨고, 설정 행의 표시가 노트를 열 때 사라진다.

Play Console 쪽에 새로 할 일은 없다. `in_app_update`는 Play 내부 API라 새 권한도,
데이터 안전성 신고 변경도 필요하지 않다.
