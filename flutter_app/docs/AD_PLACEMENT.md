# AD_PLACEMENT.md

광고 부착 위치와 노출 상한. 판정 코드는 `lib/domain/ads/`에 있고,
이 문서는 그 코드가 왜 그렇게 정해졌는지를 남긴다.

핵심 원칙 셋:

1. **탭 목적지 하나당 광고는 최대 1개.** 루틴 목록은 비워 둔다.
2. **밀어 넣는 광고와 사용자가 당긴 광고는 상한이 다르다.**
   세션 상한과 «알림 진입 금지»는 전자에만 건다.
3. **같은 형식을 한꺼번에 켜지 않는다.** 리텐션이 흔들렸을 때
   원인을 가릴 수 없게 된다.

---

## 단계

| | Phase 1 (비공개 테스트) | Phase 2 (프로덕션) | Phase 3 (유료화) |
|---|---|---|---|
| 슬롯 | A 네이티브 · B 보상형 | + C 네이티브 | 변화 없음 |
| 광고 단위 | 테스트 ID | 실제 ID | 실제 ID |
| 워밍업 | 0시간 | 48시간 | 48시간 |
| 계측 | Firebase Analytics 동반 | 슬롯별 비교 | 전환율 |
| 관문 | A가 D7 리텐션을 깎지 않을 것 | D30 리텐션 20% | — |

Phase 3에서 `FeatureGateService`가 생기면 `AdSlotPolicy`는 그 안으로
흡수된다. 결제 즉시 A·C는 사라지고, B는 시즌 테마 체험용으로 남는다.

> 이 문서는 `BUSINESS_MODEL.md` 1장·7장 개정과 짝이다.
>
> **문서 쪽은 끝났다.** `PRIVACY_POLICY.md`와 `../../docs/privacy/index.html`은
> AdMob·광고 ID·UMP 동의를 밝히도록 고쳤다(2026-09-08). 광고가 들어간 빌드가
> 이 브랜치이므로 «없음»은 더는 정확한 답이 아니다.
>
> **남은 것은 Play Console 세 곳이며, 빌드를 올리기 전에 한다.**
>
> - 앱 콘텐츠 > 광고: **광고 포함**
> - 데이터 안전성: **기기 또는 기타 ID(광고 ID) 수집 — 광고 목적, 공유함**
> - 개인정보처리방침 URL: GitHub Pages 배포까지 끝났는지 확인
>
> 선언과 실제 SDK가 어긋난 채 출시되면 정책 위반으로 앱이 정지된다.
> 되돌리는 비용이 가장 큰 항목이라 순서를 지킨다.

## 슬롯

### Slot A — 홈 · 네이티브 · Phase 1

**자리:** '다음 일정' 목록 마지막 카드 뒤 (`home_screen.dart`)

**왜 네이티브인가.** 이 자리는 이미 `AppRoutineRow` 카드가 세로로 쌓인
목록이다. 네이티브는 카드 한 장이 더 붙은 형태가 되어 레이아웃 문법을
깨지 않는다. 배경색·라운드·텍스트 스타일을 앱이 지정할 수 있어,
`BUSINESS_MODEL.md`가 광고를 기각한 근거("파스텔 톤 UI를 직접 훼손")를
피해 가는 유일한 형식이다.

**왜 이 자리인가.** 홈은 가장 많이 열리는 화면이라 노출량이 여기서 나온다.
다만 스크롤을 내려야 닿는 자리라 첫 화면 정보는 건드리지 않는다. 목록의
끝이라 사용자가 찾던 정보를 광고가 가로채지도 않는다.

**왜 세 슬롯 중 이것부터인가.** 검증이 실제로 필요한 유일한 자리다.
보상형은 Google이 그리는 전체 화면이라 레이아웃 위험이 없지만, 네이티브는
앱 화면 안에 들어오므로 카드 깨짐·오탭·동의 흐름을 실기기로 봐야 한다.

**금지 영역 (통째로):** 포커스 스트립 · 원형 시간표 · 액션 바.
정보 우선순위 1~4위는 `PROJECT_RULES.md` 9장이 정한 것이다.
완료/나중에/스킵 버튼과 광고 사이는 **최소 48dp** — 오탭 유발 배치는
AdMob 정책 위반이다. 현재 구조에서는 32px 여백 + 섹션 헤더 + 목록이
사이에 들어가 자연히 확보된다.

**미노출 조건:** '다음 일정'이 비어 있을 때. 그때는 목록 대신 캡션 한 줄만
나오는데, 그 뒤에 광고를 붙이면 광고가 그 섹션의 본문이 된다.

### Slot B — 캐릭터 팩 · 보상형 · Phase 1

**자리:** 광고로 여는 캐릭터 팩(지금은 푸들 정원 팩)의 상세 화면에서
«광고 보고 하루 써보기»를 눌렀을 때 (`character_pack_detail_screen.dart`)

**"광고 보고 하루 써보기"** — 누른 사람에게만. 하루 3회까지. 끝까지 보면
본 시각부터 24시간 동안 팩을 쓰고, 바로 적용한다. «오늘 자정까지»로 두면
밤늦게 본 광고가 몇 분짜리가 되므로 24시간으로 둔다.

**iOS는 무료로 푼다.** AdMob에 iOS 앱을 등록하기 전이라 광고를 켤 수 없는데,
그렇다고 팩을 잠가 두면 여는 방법이 없는 버튼이 된다. 판정은
`RewardedTrialOwnership`이 한다.

**왜 보상형인가.** 강제 노출이 아니라 교환이다. 사용자가 먼저 누르므로
**리텐션 위험이 구조적으로 0**이고 — 안 누르면 만날 일이 없다 — 형식 중
eCPM은 가장 높다. Pro 구매 후에도 살아남는 유일한 형식이다.

**왜 Pro를 기다리지 않는가.** 잠긴 팩이 꼭 Pro 기능일 필요는 없다.
팩 하나를 광고로 여는 팩으로 만들면 결제 스택 전체가 빠진다. 필요한
것은 팩 1종 · 만료 타임스탬프 · 얇은 게이트뿐이다.

**이 슬롯이 진짜 벌어오는 것.** 수익보다 숫자다. 몇 %가 테마 하나를 위해
30초를 내는지가 Phase 3의 평생 이용권 가격 근거가 된다. 꾸미기에 시간을
내는 비율은 꾸미기에 돈을 내는 비율을 예고한다. `BUSINESS_MODEL.md` 8장의
"전환율 2~5%"를 검증 없이 믿고 가는 것보다 낫다.

**잠긴 팩은 숨기지 않고 잠금 상태로 보여준다** — `PROJECT_RULES.md` 9장.

### Slot C — 오늘의 진행 · 네이티브 · Phase 2

**자리:** '예정' 그룹 바로 앞 (`today_progress_screen.dart`)

**왜 지금이 아닌가.** A와 같은 형식을 같은 방식으로 붙인 것이라 검증
가치가 중복된다. 반면 세션 상한이 2인데 네이티브 슬롯도 2가 되면 사실상
매 세션 둘 다 뜬다. 첫 광고 릴리스에서 그렇게 켜면 리텐션이 떨어져도
어느 쪽 탓인지 못 가린다. 잃는 건 몇 주치 노출이고, 얻는 건 되돌릴 수
있는 판단이다.

**왜 루틴 목록이 아니라 여기인가.** 진행 탭이 방문 빈도가 더 높다.
루틴 목록은 관리 화면이라 자주 열리지 않고, FAB('루틴 추가')이 떠 있어
하단에 광고를 두면 겹쳐서 오탭이 난다.

**왜 하필 '예정' 앞인가.** 그룹 경계는 읽기 흐름이 이미 끊기는 지점이다.
완료한 루틴 사이에 끼우면 자기 성취를 광고가 잘라먹으므로, 항목 사이가
아니라 그룹이 바뀌는 자리에만 넣는다. 경계가 여럿일 때 '예정' 앞을 고른
이유는 완료·진행 중이 "지금까지 + 지금"으로 한 덩어리이고 예정부터가
"앞으로"이기 때문이다. 무엇보다 **'진행 중'은 지금 하고 있는 일**이라
홈의 포커스 스트립과 같은 급의 정보다. 그 앞을 광고로 막지 않는다.

> 원안은 "'완료' 그룹과 '예정' 그룹 사이"였다. 실제 그룹은 다섯 개
> (완료 → 진행 중 → 예정 → 건너뜀 → 놓침)이고 앞의 셋은 비어 있어도
> 항상 렌더된다. 원안 문구를 그대로 옮기면 '완료 ↔ 진행 중' 경계가 되어
> 진행 중을 광고가 가린다.

**미노출 조건:** 오늘 루틴 4개 미만. 리스트가 짧으면 화면에서 광고가
차지하는 비중이 커진다. 짧은 하루에는 뜨지 않는다.

## 노출 상한

슬롯 수와 노출 수는 다르다. 자리를 늘리는 만큼 상한을 같이 걸어야
체감 광고량이 늘지 않는다. 값은 `AdPlacementCaps`에 있다.

| 상한 | 값 | 적용 대상 | 이유 |
|------|-----|-----------|------|
| 세션 총 노출 | 2회 | 네이티브만 | Phase 2에서 A와 C를 모두 보더라도 거기까지 |
| 슬롯당 세션 노출 | 1회 | 네이티브만 | 스크롤을 오갈 때마다 소재가 바뀌면 화면이 불안해진다 |
| 설치 직후 | 48시간 0회 | 네이티브만 | 앱이 습관이 되기 전까지는 띄우지 않는다 |
| 알림·위젯 진입 세션 | 0회 | 네이티브만 | "지금 이걸 할 시간"이라고 불러놓고 광고를 띄우면 알림을 꺼버린다 |
| 보상형 | 하루 3회 | 보상형만 | 사용자가 당긴 광고라 세션 상한 대신 하루 횟수로 제한 |

**보상형이 세션 상한 · «알림 진입 금지» · 워밍업의 대상이 아닌 이유:** 셋 다
사용자가 원하지 않았는데 나타나는 광고를 막기 위한 것이다. 알림으로
들어왔더라도, 설치 첫날이라도, 잠긴 팩에서 광고 버튼을 누른 것은 본인
의사다. 여기까지 막으면 기능이 사라진 것처럼 보인다.

**워밍업 48시간은 비공개 테스트에서 0으로 끈다.** 테스터의 관심은 앞쪽
며칠에 몰리므로, 48시간을 그대로 두면 상당수가 광고를 한 번도 못 본 채
14일이 끝난다 — 검증하려고 넣은 광고가 검증되지 않는다.

```bash
# 비공개 테스트
flutter build appbundle --release --dart-define=AD_WARMUP_HOURS=0
# 프로덕션 (Phase 2)
flutter build appbundle --release --dart-define=USE_TEST_ADS=false
```

## 넣지 않는 자리

| 자리 | 이유 |
|------|------|
| 루틴 목록 화면 | FAB('루틴 추가')과 겹쳐 오탭이 난다. 관리 화면이라 방문 빈도도 진행 탭보다 낮다 |
| 설정 최하단 배너 | 체류 3초 앱에서 배너는 수익 기여가 작은 반면, 파스텔 톤을 깎는 비용은 그대로 낸다 |
| 전면 광고 | 유일하게 사용자를 가로막는다. D30 리텐션 20%를 넘긴 뒤에 다시 판단한다 |
| 보상형 전면 | 앱이 알아서 띄우고 사용자는 건너뛰기만 고른다. 사실상 전면 광고다 |
| 앱 오프닝 광고 | "지금 뭐 할 차례지"를 확인하는 3초를 통째로 소비한다. **영구 제외** |

## 광고 단위 ID

기본값은 언제나 안전한 쪽이다 — `AdConfig.useTestAds`의 기본값이 `true`다.

깜빡했을 때의 결과가 이렇게 갈리기 때문이다:

- 기본값이 실제 광고였다면 → 지인 테스터의 클릭이 무효 트래픽이 되어
  **AdMob 계정이 정지된다. 되돌릴 수 없다.**
- 기본값이 테스트 광고면 → 프로덕션 수익이 0이다. 하루면 알아채고 고친다.

App ID는 테스트/실제 구분이 없다. 매니페스트에는 항상 실제 App ID가
들어가고, 테스트냐 아니냐는 **광고 단위 단위로** 갈린다.

## 코드

| 파일 | 역할 |
|------|------|
| `domain/ads/ad_slot.dart` | 자리 정의. `enabled`가 Phase를, `isUserInitiated`가 상한 대상을 가른다 |
| `domain/ads/ad_placement_caps.dart` | 상한 숫자. 정책을 바꾸려면 여기만 고친다 |
| `domain/ads/ad_slot_policy.dart` | 순수 판정. 저장소도 시계도 만지지 않는다 |
| `domain/ads/ad_slot_decision.dart` | 결과 + 거절 사유. 광고가 안 뜨는 게 버그인지 상한인지 가른다 |
| `application/services/ad_policy_service.dart` | 세션 상태를 들고 정책에 묻는 창구. 화면은 여기만 본다 |
| `application/services/ad_config.dart` | 빌드 주입 설정 |
| `data/local/ad_local_storage.dart` | 첫 실행 시각, 보상형 하루 횟수 |
| `application/services/rewarded_ad_service.dart` | 보상형 로드 · 표시. 끝까지 봤는지를 돌려준다 |
| `domain/store/pack_trial.dart` | 광고로 연 팩의 소유 판정 · 24시간 |
| `data/local/pack_trial_storage.dart` | 팩마다 체험이 끝나는 시각 |
